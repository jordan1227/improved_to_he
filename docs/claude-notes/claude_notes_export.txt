Suit/mask balance philosophy — ongoing
- [stated] Design philosophy: Duty suits focus on psy and wound (anti-mutant) protection but are bulkier with worse anomaly protection; Freedom is lighter/more mobile with better anomaly protection but worse psy screening, wound protection, and durability; Mercs are durability-focused with emphasis on explosion and fire_wound (bullet) protection; Monolith suits are the "ultimate version" per in-game lore (made from unknown materials); ecolog_outfit is the basic scientist suit with protection_outfit as its improved version; scientific_outfit (Neutral SEVA) is the base loner scientific suit
- [stated] Tesla location deals periodic electric/shock damage to the player; electric anomalies are otherwise easily avoidable, and electric poltergeists (which have a shock aura) are uncommon and mostly expected in labs
- [stated] Labs require a special breathing suit: all scientific suits, plus two exceptions — SKAT-10 (militaryspec_outfit) and the monolith exoskeleton (monolit_exoskeleton)
- [stated] Design idea: SKAT-10 and CS-3a (cs_heavy_outfit) cost the same in barter (both require the most exceptional artifacts); SKAT-10 is meant to be top-tier physical damage resistance with decent durability and lab access, while CS-3a is meant to be more mobile and better suited for Tesla, without lab access
- [stated] On northern maps, dirty air means the player is masked roughly 90% of the time, taking periodic damage otherwise

Mask/armor-swap and load-time stat bugs (`sivol_masks.script`) — resolved

=== /areas/ogse-signals-system.md ===
---
name: ogse-signals-system
description: How event/signal subscription actually works in NLC OGSR HE (ogse_signals) — reusable technical reference, not project-specific narrative
sources: [chat]
aliases: [ogse_signals, am system, self.am, hud anim subscriptions, on_key subscription]
---
- [stated] There is exactly one dispatch mechanism for anything event-like in this fork: `ogse_signals`. `self.am` (seen in `bind_stalker.script`, e.g. `self.am:call("on_actor_before_hit", ...)`) is NOT a separate "action manager" — it's the same `ogse_signals` manager instance used for `on_update` and everything else. Confirmed via an engine-source trace the user provided (GLM 5.2 analysis of `ogse_signals.script`/`bind_stalker.script`).
- [stated] There is no auto-discovery by function name anywhere in this system. A bare global function, even one exactly matching a signal name, is never invoked on its own — `signals_mgr:call(signal_name, ...)` only walks slots explicitly registered via `mgr:subscribe({signal=..., fun=...})`.
- [stated] Correct pattern: define handler(s) as local functions, then `function attach(sm) sm:subscribe({signal="name", fun=handler}) end`, expose as `module.attach = attach`, and list the module's name in `ogse_signals_addons_list.addons` (or `attach` never runs). `auto_attach = true` only works for files literally named `ogse_*.script` (filesystem glob), not a general mechanism.
- [stated] Confirmed working signal names via this mechanism: `"on_update"` (fires every frame; self-throttle via `ogse_signals.get_mgr():reschedule(ms)` inside the handler if desired, but NOT for anything driving `play_hud_anm` — that needs per-frame calls to blend smoothly, throttling causes visible choppiness); `"on_actor_before_hit"` (handler receives `(obj, hit_data, binder)`); `"on_actor_weapon_zoom_in"`/`"on_actor_weapon_zoom_out"` (fire on ADS enter/exit, though polling `wpn_params.get_zie_obj() ~= nil` directly — same check `scope_wobble` uses — proved more reliable for aim-state detection in practice); `"on_key"`/`"on_key_up"` (fire on keypress/release, receive `(key, bind)`, `bind` matches `key_bindings.*` entries e.g. `key_bindings.kCROUCH`, `key_bindings.kCROUCH_TOGGLE`).
- [stated] Prefer event-driven signals (`on_key`/`on_key_up`) over `on_update`-based state polling for anything needing a crisp one-shot reaction to a state transition — polling for stance changes and firing one-shot `play_hud_anm` calls from `on_update` raced against the engine's own movement/animation state machine and got silently overwritten before rendering; firing from the actual keypress event fixed it.
- [stated] Toggle-bind gotcha: don't trust `is_actor_crouch()`/`is_actor_creep()` read live inside an `on_key` handler to decide toggle direction — those flags can lag behind rapid key-spam, causing every-other-press to read stale state and misfire. Track the toggle state in a local boolean flipped once per keypress instead, independent of the engine's flags. Even with this fix, extremely rapid spam can still show a softer "cooldown" feel, suspected to be the native animation system's own retrigger/blend timing on the same partial-anim channel rather than something controllable from script — increasing playback speed shrinks the window but may not fully eliminate it.
- [stated] Confirmed death-related signals (from `anomaly_detector.script`/`xr_kamp.script` usage and `bind_monster.script`'s `generic_object_binder:death_callback`, which calls `self.am:call("on_monster_death", self.object, who)` — reconfirming `self.am` as the `ogse_signals` manager): `"on_npc_death"`, `"on_monster_death"` (handler receives `(object, who)`, fired at the moment of death) and separately `"on_npc_net_destroy"`/`"on_monster_net_destroy"` (fired on object removal from the level, e.g. corpse decay via `nlc_corpse_decay` — can fire well after actual death, so not a substitute for the death signals if the goal is reacting to the moment of death). No actor-specific death signal has been confirmed yet; workaround is edge-detecting `db.actor:alive()` transitioning true→false inside an `"on_update"` handler instead of needing one.
- [stated] `ogse_signals_addons_list` (the file listing modules needing explicit registration) is a plain Lua `addons = {...}` table of module name strings — only modules whose filename does NOT start with `ogse_` need to be listed here (those are auto-attached by filesystem glob, per the existing note above). Custom/ported HE-specific modules (e.g. `sivol_weapon`, `sivol_weapon_inertia`) are appended under a `-- [HE-PORT]` comment section within that same table — new custom modules needing `attach(sm)` to fire must be added to this list, or `attach` is never called.
- [stated] This reference originated from debugging `sivol_weapon_inertia.script` (see [[nlc-he]]) but the subscription mechanics apply to any future NLC OGSR HE scripting needing engine event hooks.
- [stated] `bind_stalker.script` wires genuine native engine callbacks into this same `self.am`/ogse_signals dispatch: `self.object:set_callback(callback.X, self.X, self)` registers a native engine callback, and the handler method then does `self.am:call("mapped_signal_name", ...)` to relay it as an ogse_signal. Confirmed native "before" callbacks wired this way (from `lua_help.script`'s callback const table): `on_before_save`=52, `entity_alive_before_hit`=42, `on_before_use_item`=41, `on_before_switch_torch`=76, `on_before_switch_nv`=77.
- [stated] Confirmed (full function body from user): `actor_binder:on_item_take(obj)` and `actor_binder:on_item_drop(obj)` bracket their own logic with `self.am:call("on_take_before_all"/"on_take_after_all", obj, server_obj(obj:id()))` (and drop equivalents) — these are NOT a veto point. By the time `on_item_take` runs at all, the engine has already completed the pickup natively; "before_all"/"after_all" only means "before/after this function's own extra processing (dog_psy tracking, arc_arts hook, batched taked_items table)", not before/after the actual item transfer. There is no native "before pickup, can cancel/delay" hook in this engine analogous to Anomaly's `actor_on_item_before_pickup` — confirmed dead end for that approach.


=== /areas/nlc-fdda-anim-porting.md ===
---
name: nlc-fdda-anim-porting
description: Reusable technical reference for porting FDDA (Anomaly) HUD/camera animations into NLC OGSR HE — confirmed engine quirks, asset pipeline steps, and pitfalls from the backpack-pickup animation port
sources: [chat]
aliases: [FDDA port, HUD motion, play_hud_motion, motion_refs, anim_items.ltx, backpack pickup animation, liz_backpack]
---
Originates from porting FDDA's backpack-equip animation (Anomaly) into a backpack-pickup animation for [[nlc-he]]'s shadow_inventory/drop-rucksack system (nlc_container.script). Previously successfully ported FDDA helmet/headgear animations the same way, so the pipeline below is proven working, not just theoretical.

## Asset pipeline (per FDDA source item)
FDDA splits each animated item's assets across four locations that must ALL be ported together, correctly split:
- `anims\itemuse_anm_effects\*.anm` — camera effector clip
- `meshes\anomaly_weapons\hud_animation\*.omf` — ITEM-side motion tracks (paired with the visible item mesh, e.g. the backpack itself)
- `meshes\anomaly_weapons\hud_hands_animation\*.omf` — HAND-side motion tracks (paired with the player's hand skeleton)
- `meshes\anomaly_weapons\<category>\*.ogf` — per-faction HUD meshes (multiple .ogf variants exist per item, e.g. liz_backpack_hud_army.ogf, _bandit.ogf, etc. — these are NOT different item models, they exist because the visible hands/sleeves in the first-person view must visually match the actor's current faction/outfit skin)
- Matching `.ogg` sound(s) under `sounds\actor\`

Do not dump `.ogf`+both `.omf` files into a single flat folder — mirror FDDA's split structure (hud_animation / hud_hands_animation / item mesh folder are three separate locations), or motion lookups will fail or crash.

## Confirmed OGSR-vs-Anomaly engine differences
- **OGSR ignores the `motion_refs` field inside LTX HUD sections.** Anomaly's engine reads `motion_refs = <path>` in a .ltx section and dynamically loads that .omf; OGSR does NOT do this — the reference is silently ignored, so animations "not found" even though the .ltx section is otherwise correct.
  - Fix: embed the additional motion reference directly into the target .ogf's own embedded "Motion References" list (edited in the mesh itself, not the .ltx) so OGSR loads it natively as part of the mesh.
- **Bone-count mismatch crash**: embedding an item-only motion track (17 bones, e.g. `hud_animation\liz_backpack`) into the PLAYER HAND mesh's motion references (42-bone hand skeleton) causes a `motions_value::load` fatal error: "Invalid remap index!"
  - Fix: item-only tracks go into the item's own hud .ogf (e.g. `liz_backpack_hud.ogf`) motion references. Hand-appropriate tracks (e.g. `hud_hands_animation\liz_backpack_hands`) go into the PLAYER HAND .ogf's motion references instead. Don't mix which mesh gets which track.

## anim_items.ltx section gotchas
- The animation-name VALUES in a line like `anm_equip = liz_backpack_hud_equip_hands, liz_backpack_hud_equip` must exactly match the clip names physically baked inside the ported .ogf/.omf files. You can freely rename the .ltx SECTION name and the KEY name (e.g. `anm_equip` vs FDDA's `anm_use`), but NOT these value strings — renaming them without re-exporting/re-baking the actual clips causes a fatal `player_hud_motion_container::load ... motion [X] not found in section [Y]` crash.
- `game.play_hud_motion(slot, hud_section_name, key_name, bool, speed, bool)` — the 3rd argument is the LTX KEY name (e.g. `"anm_equip"`), not the raw clip name values from the ltx line.
- Full 6-argument signature matters. Every known-working full-length animation in this codebase (vergas_masks.script equip/unequip, sak.script's generic play_item_use) calls it as `(slot, section, key, true, speed, true)` — arg4 and arg6 both `true`. A call using `(slot, section, key, false, speed)` (arg4 false, arg6 omitted) correlates with the played animation fully locking player movement/camera/actions for its whole duration, unlike the masks flow which only applies a movement-speed penalty and leaves movement/camera free. Not fully confirmed as causal yet, but consistent across every example seen so far — try matching the full `true, speed, true` signature first when movement/camera lock is unwanted.
- `item_visual` and any `motion_refs`/asset paths in the .ltx are relative to the meshes root — match the exact relative path convention of the source engine's own working sections (e.g. `anomaly_weapons\...` if that's where the asset actually lives, not `dynamics\...` unless the asset is actually under that subtree). A wrong-but-plausible-looking path fails silently rather than erroring clearly.

## Scripting/scheduling gotchas (dsh.timeout / ogse_qt)
- Calling `dsh.timeout(...)` (nested) from inside a callback that is ITSELF currently executing as part of an active `ogse_qt` timer-processing pass can throw a Lua `invalid key to 'next'` engine-level fatal error — this is a table-mutation-during-iteration issue (inserting a new timer into ogse_qt's internal timers table while it's being iterated). Existing code (vergas_masks.script) nests multiple `dsh.timeout` calls from one callback without issue, so this doesn't always trigger, but it's a known possible crash cause worth knowing about if a similarly-shaped crash shows up during a future port.
- See [[ogse-signals-system]] for the separate, already-documented `ogse_signals`/`self.am` subscribe/unsubscribe API contract (`mgr:subscribe({signal=..., fun=...})` returns a handle, unsubscribe via `mgr:unsubscribe(handle)` from outside — do NOT assume the handler receives a self-referencing subscription object with its own `:unsubscribe()` method, that is not the confirmed API shape).

## Structural note specific to this port
NLC HE has no dedicated backpack equip-slot (unlike FDDA/Anomaly, where backpacks occupy an outfit slot). Backpacks in NLC are drop/pickup-only entities via shadow_inventory (nlc_container.script). The FDDA equip-animation assets/flow were adapted onto NLC's pickup flow by treating "pick up dropped rucksack" as the functional equivalent gesture to FDDA's "equip backpack" — reusing the same ported assets rather than authoring a separate pickup-specific animation.

## UI/window integration convention (confirmed, from document-read animation port)
This codebase does not use lam2 (FDDA's action-queue system) or generic GUI_on_show/GUI_on_hide signal watching for custom windows. Convention here is: CUIScriptWnd-derived window classes own their own on_quit, and anything needing to react to open/close is called directly from that window class's own methods (or via ogse_signals for genuinely cross-system events, e.g. on_inventory_hide). When porting an FDDA feature that ties an animation to a UI opening/closing, expose plain show()/hide() trigger functions for the window class to call directly, rather than trying to hook a generic UI-visibility signal.

name: nlc-adaptive-scope-zoom
description: Investigating a dynamic per-weapon-class ADS FOV offset system for NLC OGSR/Improved HE — making scope_zoom_factor relative to the player's FOV slider instead of a fixed absolute value; mid-investigation of OGSR engine C++ source, not yet implemented

## Goal
- [stated] Weapon ADS zoom (`scope_zoom_factor` in gamedata/config/weapons) is currently a static per-weapon value, disconnected from the player's FOV slider — a high-FOV player gets a much stronger relative zoom than a low-FOV player from the same weapon. User wants a system where each weapon class has a relative offset from the player's current FOV setting instead (e.g. pistols always -5 FOV from base, assault rifles -2), so ADS zoom feels consistent regardless of the player's FOV slider value.

## Confirmed from OGSR-Engine-main C++ source (user has source access, base OGSR unmodified in this fork for this system)
- [stated] `CWeapon::m_fScopeZoomFactor` is bound read/write to Lua directly: `derived_client_classes.cpp:397` — `.def_readwrite("scope_zoom_factor", &CWeapon::m_fScopeZoomFactor)`. It's a live per-weapon-instance engine property, settable from script at runtime — no need to hack ini reloading to change it dynamically.
- [stated] There's a feature flag `ogse_wpn_zoom_system` (`xrCore.h` bit 25, set via `CORE_FEATURE_SET(ogse_wpn_zoom_system, "features")` in `x_ray.cpp`, i.e. toggled by a `[features]` section in some game ltx) that changes the UNITS of `m_fScopeZoomFactor`/`m_fZoomFactor` entirely:
  - OFF (legacy/vanilla-style): `def_fov = g_fov` (the actual player FOV-slider global, bound to console var "fov" via `CMD4(CCC_Float, "fov", &g_fov, 5.0f, 140.0f)` in `console_commands.cpp`). In this mode `m_fScopeZoomFactor` is an **absolute FOV value in degrees** — exactly the disconnect the user described (static number, not relative to g_fov).
  - ON: `def_fov = 1.f` — in this mode the values are a **0–1 fraction system** instead, implying a different (likely multiplicative-against-current-fov) formula elsewhere.
  - Still unconfirmed which mode this NLC/OGSR-Improved build actually has enabled — needed before writing the real formula.
- [stated] `CWeapon::GetZoomData()`/`ZoomChange()` (`Weapon.cpp` ~1260-1300) is the **scroll-wheel variable-zoom stepping** logic — steps `m_fZoomFactor` from `def_fov` toward `m_fScopeZoomFactor` over `m_fZoomStepCount` discrete steps, clamped via `m_fMinZoomK`. Not yet confirmed whether plain single-step ADS (non-adjustable scopes, e.g. iron sights/pistols) reuses this same path or a separate simpler assignment elsewhere.
- [stated] `Is3dssEnabled()` weapons (3D scope system) bypass `ZoomChange()` entirely — a code comment says variable magnification for "new scopes" was reimplemented in script instead of engine (Russian comment: "made variable magnification for new scopes in scripts, might return it to the engine later"). Possible existing script-side precedent for reading/writing zoom factor worth finding.
- [stated] `CHudItem::CWeaponBobbing::Update()` also consumes `m_fZoomFactor`/`m_fScopeZoomFactor` as a hand-bobbing amplitude multiplier during zoom (`k2 *= zoom_factor`) — a secondary consumer, not the camera FOV assignment itself.

## Resolved — final confirmed formulas (build has ogse_wpn_zoom_system=false, per gamedata/config/external.ltx)
- [stated] `CActor::currentFOV()` (Actor.cpp): when zoomed and feature OFF, returns `pWeapon->GetZoomFactor() * 0.75f`; `GetZoomFactor()` returns `m_fZoomFactor`, which snaps to `m_fScopeZoomFactor` on ADS start. So `zoomed_camera_fov = scope_zoom_factor * 0.75`, fully independent of `g_fov` (the FOV slider, bound to console var "fov") — this is the confirmed root cause of the original complaint.
- [stated] Final formulas: unscoped `new_scope_zoom_factor = (current_fov - class_offset) / 0.75`; scoped `new_scope_zoom_factor = base_scope_zoom_factor * (current_fov / 67.5)` (67.5 = engine's hardcoded default `g_fov`, `Actor.cpp`).
- [stated] Critical compounding-drift fix: base value for the scoped formula must come from an immutable ini source, never read back from `wpn.scope_zoom_factor` after this script starts writing it. Confirmed via a sample `add_scopes.ltx` entry (`wpn_addon_1pso`, `scope_zoom_factor = 20`) that scope magnification is authored on the **scope addon's own ini section**, looked up via `wpn.scope_name` (exported as `m_sScopeName`), completely separate from the weapon's own section value — a scope's magnification can differ entirely from the weapon's bare value, so caching the weapon's own value is wrong once a scope's involved.
- [stated] Scope-attached detection: `ogse_wpn_utils.get_scope_status(wpn)` (0=none, 1=integrated/fixed, 2=detachable) + `ogse_wpn_utils.get_scope_flag(wpn)` (`bit_and(wpn:get_addon_flags(), addons_flags.scope) ~= 0`) for the detachable-but-currently-absent case — this existing utility already implements exactly what's needed, no need for `IsScopeAttached()` (confirmed not exposed to Lua).
- [stated] `weapon.zoom_factor` and `weapon.scope_zoom_factor` are exported as plain readwrite fields (not methods) — `wpn.scope_zoom_factor = x` is valid directly. `GetZoomFactor()`/`IsScopeAttached()`/`IsGrenadeMode()` are NOT exposed to Lua.
- [stated] `wpn_params.get_zie_obj()` returns a zoom-in *effector* object (`find_effector_zi()`), not the weapon — confirmed NOT usable as a weapon-object shortcut; must get the active weapon separately via `db.actor:active_slot()` + `db.actor:item_in_slot(slot)`, then `item:get_weapon()` for the CWeapon-bound object needed to write the field.
- [stated] Draft implementation written to `sivol_adaptive_zoom.script`, edge-triggered off the aim-state transition (same `get_zie_obj() ~= nil` polling pattern already proven reliable elsewhere in this codebase — see [[ogse-signals-system]]) rather than the `on_actor_weapon_zoom_in` signal. Needs registration in `ogse_signals_addons_list`'s `addons` table (`-- [HE-PORT]` section) to fire at all.
- [stated] Weapon class table (pistol/rifle/smg/shotgun/sniper/lmg) in the draft script is seeded from a filename-based guess (another LLM's inference from real-world weapon knowledge, not sourced from an actual in-game class/kind ini field) — flagged as needing audit; only pistol (-5) and rifle (-2) offsets are user-confirmed, others are placeholders.

## Unverified, flagged for testing/follow-up
- [stated] `ini_file():line_exist(section, param)` — assumed method name for checking a key exists before `r_float` read; not confirmed against actual bindings.
- [stated] `item:get_weapon()` on a raw inventory item from `db.actor:item_in_slot()` — confirmed to exist somewhere in `ogse_wpn_utils` usage the user showed, but not confirmed as generally callable on any item object.
- [stated] Whether the edge-triggered recompute (on aim-state transition) actually lands before the native zoom snapshot reads `scope_zoom_factor` each ADS-enter, or whether there's a one-cycle lag — not yet tested in-game.

## Current live architecture (as of this session)

- [stated] `scale_artefact_stats(item, reset)` writes every restore-speed + immunity + weight prop fresh from ini base each call (never mutates an already-scaled stored value — kills the old compounding-bug class); `reset=true` (base/unscaled) used for off-belt artifacts and on spawn

- [stated] Design decision, now made explicit via toggle rather than hardcoded: whether a debuff stat (radiation, hunger drain) rides the same condition+tier-bonus curve as buffs (`use_buff_formula_for_X=true`, "artifact stays dangerous/costly longer as it wears, matching its bonuses staying strong longer") or decays plain-linear with condition (`=false`) is intentionally left as a runtime toggle since balance isn't finalized — every consumer must go through `get_effective_strength`/`get_effective_strength_raw` (never a raw `* condition`) so the toggle is actually respected everywhere; user explicitly wants this enforced project-wide including garbage_arts and all UI displays

- [stated] Vanilla OGSR's `check_artefact()` called `max_item_mass_add(0)` (hardcoded zero) — stock artifact carry-weight was never applied through that actor-level aggregate at all; the real native mechanism is per-item `additional_inventory_weight2` property assignment (same as outfits use via `obj:set_additional_max_weight()`), which is why routing scale_artefact_stats's weight write through that property (plus firing it on the belt-enter/leave signal instead of only a delayed poll) fixed the instant-update bug
- [stated] NLC's dyn1d–dyn6d tier system is not a computed bonus in the ini data itself — each tier is a separate hardcoded item section; the tier-bonus curve this system adds is a scaling layer on top of already-tiered base values, not a replacement for them
- [stated] Two-tooltip discovery: a near-cursor tooltip (`ui_inv_descr.script`'s `ShowAfParams`, main inventory) was already rewritten early this project to compute fresh from ini+get_effective_strength; the container UI's `get_art_info_text` was the one still lagging (now fixed this session)

- [stated] GLM 5.2 produced finalized ready-to-paste code for `_g.script` (core), `arc_radiation.script` (2 sites), and `ui_arc_container_menu.script` (4 sites + full `get_art_info_text`) implementing everything agreed this session; Claude reviewed it line-by-line against its own proposed diffs and confirmed it matches exactly, no errors found — toggles currently set `use_buff_formula_for_radiation = false` / `use_buff_formula_for_hunger = false` (plain-linear for both debuffs, the already-tested/confirmed behavior), easily flippable later once balance is decided
- [stated] Confirmed via architecture review (not yet an in-game test) that garbage_arts.script needs NO edits: it already writes the canonical deterministic radiation value once via `update_prop` + `ui_arc_container_menu.xp_write` at pickup time (and re-affirms it on `on_game_loaded` for previously-flagged artifacts); `scale_artefact_stats` picks that value up via `xp_read` and layers the normal condition/toggle scaling on top of it as the "base" instead of the ini value — clean separation of concerns (garbage_arts owns the canonical baseline, scale_artefact_stats owns the condition scaling), no double-maintenance needed.
